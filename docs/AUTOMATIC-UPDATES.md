# Signed automatic theme updates

Lumen's update page can check the latest published stable release, download it on the router, verify it and install it. The browser must remain open until the refreshed page confirms that the theme and its resources load. A failed installation or an unconfirmed page causes the previously installed, signed release to be restored. A separate watchdog covers an updater process exiting unexpectedly, and a small boot hook attempts recovery if the router restarts with an update pending. The last verified previous package is also available through **Restore previous version**.

The updater does not change DNS, firewall or proxy rules. It first attempts a direct HTTPS connection. If that fails and OpenClash is enabled, it tries the configured local HTTP proxy and its first enabled authentication entry. Proxy credentials remain on the router and are supplied to `curl` through standard input. Other proxy implementations are not discovered automatically. The browser's separate release-history button still uses the browser's own connection.

All URLs, package names and actions are fixed by the updater. The project usign public key embedded in the installed theme verifies the release manifest; each package and firmware build-information file must match that signed manifest. On APK systems, each package must additionally pass the native project-key signature check. The project's APK key is used only in a temporary transaction key directory, not added to the system trust store. Unexpected keys, missing old packages, mismatched firmware or missing tools stop the update. The firmware version and package format must exactly match the signed build information; architecture independence does not imply compatibility with other OpenWrt or LuCI versions.

The updater retains the installed Chinese translation and optional font package when present. It preflights both package transactions, preserves theme configuration, and keeps a verified rollback set under `/etc/lumen-updater`. A successful new update replaces the prior rollback set. It uses `curl`, `usign`, `flock` and `rpcd-mod-ucode` in addition to the normal theme dependencies; there is no permanent polling daemon. The boot hook remains available for recovery, and update-related watchdog processes exit once the transaction is complete.

The automatic updater first has to be installed in a verified Lumen package. A release predating the updater cannot update itself through this page. In particular, restoring v1.0.2 restores its older download-only update page. If a previous version cannot be authenticated with the installed updater's project keys, automatic update stops rather than guessing how to recover it. Key rotation must be handled explicitly through an independently verified installation or a transition signed by the previously trusted key.

For maintainers: every stable release intended for automatic update must retain the signed `SHA256SUMS` and `SHA256SUMS.sig`, the exact package names, and signed `BUILDINFO-openwrt-<release>.json` assets for each supported package format. Do not delete the preceding release assets needed for rollback. Check that the version and release number in the built packages match the published names. Maintain the existing trust anchor or document and authenticate any transition before publishing.
